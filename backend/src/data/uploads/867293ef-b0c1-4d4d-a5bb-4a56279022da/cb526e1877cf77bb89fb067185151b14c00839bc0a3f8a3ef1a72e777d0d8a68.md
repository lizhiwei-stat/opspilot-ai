# 订单服务 HTTP 500 故障排查手册

适用范围：order-service（订单服务）v2.x，负责人：订单平台组。本手册用于值班工程师在订单接口出现大量 HTTP 500 时快速定位问题。

## 1. 现象确认

先确认是服务端错误而不是网关错误。HTTP 500 表示 order-service 内部抛出了未处理异常；如果看到的是 502 或 504，通常是网关到订单服务的连接失败或超时，请转到网关排查章节。

确认步骤：
1. 在监控面板查看 order-service 的 5xx 比例，正常应低于 0.1%。
2. 按接口拆分错误，常见受影响接口是 POST /api/orders（创建订单）和 POST /api/orders/{id}/pay（支付）。
3. 记录开始时间，对比最近一次发布时间。

## 2. 常见原因

### 2.1 发布引入的空指针异常
升级后立即出现 500，并且日志中大量出现 NullPointerException，多半是新版本代码问题。v2.3.0 曾因 PaymentAdapter.charge() 未处理空的优惠券字段导致空指针异常。处理方式：确认后立即回滚到上一个稳定版本，再修复代码。

### 2.2 数据库连接池耗尽
日志出现 "Connection is not available, request timed out after 30000ms" 或错误码 ORD-5003，说明 HikariCP 连接池耗尽。常见诱因是慢查询或连接泄漏。可以临时扩容实例，并检查慢查询日志。

### 2.3 下游支付网关超时
日志出现 ERR_PAY_TIMEOUT，说明调用支付网关超过 3 秒未返回。订单服务会把该错误映射为 HTTP 500（v2.3.1 起改为 503）。应检查支付网关状态页，并确认熔断器是否已打开。

## 3. 处理流程

1. 判断影响面，P1 级故障需在 5 分钟内拉起事故频道。
2. 如果与发布时间吻合，优先回滚，回滚步骤见《部署与回滚指南》。
3. 如果是连接池耗尽，先扩容再排查慢查询。
4. 故障恢复后 48 小时内提交复盘报告。

## 4. 需要收集的信息

提交工单时请附上：错误开始时间、受影响接口、错误码、最近发布版本号、trace_id 样例以及错误日志片段。
