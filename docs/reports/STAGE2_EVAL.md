# 第二阶段检索评测报告

> **先读这一段**：本报告的数字都在 Teddy 的 WSL2 Docker Compose 栈上真实运行得到，但它们**不代表真实 RAG 效果**：
> 1. Embedding 是 **mock**（字/词特征哈希），只衡量字面重叠，**没有语义**；
> 2. 回答器是 **mock 抽取式**，没有大模型；
> 3. 语料（13 篇）和问题（55 条）都是 **AI 助手编写的合成数据**，没有人工独立标注，问题措辞和文档字面重合度偏高，会**高估**字面方法；
> 4. 规模很小，指标差 0.01–0.03 不具统计意义。
>
> 这些数字的用途是：证明评测管线可复现、ACL 无泄露、四种模式都能正确运行，并且能比较"字面信号"的相对强弱。

## 3. 解读（附带注意事项）

- **混合检索 + 重排在四种模式里最好**（Recall@5 0.957，MRR@10 0.903）。重排器用 IDF 补上了 `ts_rank_cd` 缺少的稀有词权重，错误码类问题 Recall@5 从 0.867（hybrid）升到 1.000。
- **关键词通道在错误码上明显强于 mock 向量**（0.967 vs 0.833）。原因是 `ORD-5003` 被归一化为整体 token `ord5003`，而 mock 向量把它拆成了 `ord` 和 `5003`。
- **mock 向量在"改写"类上看似不错（0.906）**，这是假象：这些问题和文档仍然共享大量单字（例如"连接""超时"）。mock 向量本质是单字重叠，并不理解语义。真正没有共享字词的改写，比如 q022"退回旧版本"对应"回滚"，在 vector 模式下 Recall@5 只有 0.5，q026 为 0.0。
- **multi_doc 类重排后反而下降**（1.000 → 0.881）。重排倾向于把覆盖查询词最多的同一文档的多个块排在前面，挤掉了另一篇文档。这是字面重排器的已知缺点，真实交叉编码器或按文档去重（MMR）可以缓解。
- **ACL 泄露 = 0**：
  - 4 种模式 × 55 条 = 220 次检索，返回的每个分块都按一张**与代码独立写定**的权限矩阵核对过；
  - 问答的 43 + 12 次回答中，引用泄露同样为 0；
  - 集成测试另外证明过滤发生在排序之前（limit=1 实验）。
- **问答的误拒全部发生在 paraphrase 类**：共 11 条，包括 q021、q022、q025–q027、q029–q034。原因是证据分数是字面覆盖率，换了说法的问题覆盖率低于 0.5。
- **误答 2 条**，都是 no_answer 类：
  - q045"订单服务用的是哪个版本的 Java"：命中了"订单服务""版本"，覆盖率 0.57；
  - q048"Redis 集群扩容步骤"：命中了"扩容""步骤"，覆盖率 0.50。
  
  这说明阈值 0.5 在这份数据上偏宽，存在明确的"误拒 / 误答"权衡。这里**没有**为了好看去调阈值，接入真实模型后应在一份独立的验证集上重新标定。
- 6 条无权限问题全部正确拒答（"证据不足"），回答中没有透露受限文档的存在。

## 5. 下一步建议（需要 Teddy 决定）

1. 授权后跑一次真实 embedding 评测。13 篇文档约 50 个分块，加上 55 条查询，调用量很小，但仍会产生费用，因此需要明确授权。
